# Accuracy, keyword search only (baseline), 2026-11-05

code_recycle 0.1.0.dev0. Weights, query building and the test design were fixed before either test
was run, and nothing has been tuned since. This is the baseline any later change must beat.

## 1. CodeSearchNet, Python (public benchmark)

Find a function from its docstring among 999 others, scored by mean reciprocal rank (MRR), as in
Husain et al. (2019), Table 3. The docstring is removed from the code before indexing.

| Measure | Result |
|---|---|
| Queries | 22,000 (22 groups of 1,000, seed 2026) |
| MRR | 0.797 |
| Right function in the top 5 | 87.3% |

Checks:
- With function names removed from the name column, MRR is 0.763, so the result doesn't rest on names alone.
- With the docstring deliberately left in the code, MRR is 0.988. That shows the removal works, and
  why it matters.
- 227 functions (1%) didn't parse, so their docstrings stayed in. 13 queries had no usable words and
  count as misses.

For context only: the paper reports Python MRR of 0.581 to 0.692 for its trained neural models. This
run uses the same protocol but its own implementation and its own random distractors, so the
numbers are not a like-for-like comparison. Docstring-to-code is a task where shared words help
keyword search a lot.

## 2. Own research entries (the job the tool was built for)

Given a research topic's heading and question, find another verified entry that used the same
source. The entry itself is removed from the search. Reuse rules are off.

| Measure | Result |
|---|---|
| Test cases | 49, from 5 projects (252 entries indexed) |
| MRR | 0.280 |
| A matching entry in the top 5 | 36.7% |
| Not in the top 200 | 11 of 49 |

What the misses show: entries often share a source but describe a different part of it in
different words (a permutation test used once as "matched null control" and once as "paired test
across folds"). Keyword search can't bridge that. It's the case meaning-based search (embeddings,
build step 6) has to improve, measured against these same 49 cases.

Per-case detail names private files, so it is not published.

## 3. Meaning search (embeddings), tested and not adopted

Pre-registered in `results/prereg_embeddings.md`, with one speed amendment made before any
accuracy run. A small local model (bge-small) was chosen on the CodeSearchNet validation split,
then run once on both tests.

| Test | Keyword (shipped) | Meaning only |
|---|---|---|
| CodeSearchNet Python test, MRR | 0.797 | 0.907 |
| Own research entries, MRR | 0.280 | 0.250 |

It had to improve both, and it didn't improve the own-entries test, so v0.1 ships keyword search.
The code is in the repository, off by default, marked experimental.

## 4. Re-run at packaging (later on 2026-11-05)

A formatting bug was fixed after the baseline: copied code in research entries kept its ``` marker
lines and lost blank lines. Re-running the keyword search with no other change to the method:

| Test | Baseline | At packaging |
|---|---|---|
| CodeSearchNet Python test, MRR | 0.797 | 0.797 (not affected: it doesn't read research entries) |
| Own research entries, MRR | 0.280 | 0.308 |
| Own research entries, top 5 | 36.7% | 39.2% |
| Own research entries, test cases | 49 from 5 projects | 51 from 6 projects |

The own-entries number moved for two reasons that can't be separated after the fact: the bug fix,
and the folder itself, which gained files during the day. The test cases are found fresh each run (entries
that share a source), so two new cases appeared. The embeddings decision above compared
like with like at the time and stands.
